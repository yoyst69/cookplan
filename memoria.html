CookPlan · Memoria del proyecto

Inicio Actualizada: 2026-09-19 · Documento vivo, se amplía en cada sesión. Estado Backend completo y probado (recetas, plan semanal, lista de la compra y tareas domésticas del fin de semana) + frontend web completo con build en verde + plataforma Android añadida con Capacitor.

1. Objetivo del proyecto

Aplicación CookPlan para el hogar: planificación semanal de comidas evitando repeticiones, generación de la lista de la compra a partir del menú y reparto de tareas domésticas del fin de semana entre los miembros de la casa (Fiti, Mar y Jose).

2. Requisitos funcionales

2.1. Usuarios

  • Registro con confirmación por correo (o enlace por consola si no hay SMTP configurado).
  • Roles: administrador (Fiti) y usuarios normales (Mar, Jose). Un admin puede crear usuarios, cambiar permisos/activo y restablecer contraseñas.
  • Usuarios iniciales (seed): Fiti admin = admin@cookplan.local / Fiti6969 · Mar = mmarruizg70@gmail.com / 5668 · Jose = jose@cookplan.local / 5668.

2.2. Recetas

  • Catálogo de recetas con foto (subida multipart → WebP mediante sharp), tiempo, personas, momento (Desayuno/Comida/Cena) y pasos/ingredientes.
  • Importación inicial de 40 recetas de Mar desde scripts/recetasDataA.ts + recetasDataB.ts (fuente: Recetas.Mar.docx convertido a texto). Importador idempotente en scripts/import-recetas.ts.

2.3. Plan semanal

  • Tabla 7 días × 2 slots (comida y cena). El generador rellena solo los huecos vacíos.
  • Regla anti-repetición: una receta no se repite si se usó en los últimos dias_sin_repetir días (config por usuario, 21 por defecto) ni en la misma semana. GET /plan/sugerencias devuelve sugerencias con diasSinUsar.

2.4. Lista de la compra

  • Origen MENU (generada desde el plan, agrupando ingredientes) y MANUAL (productos añadidos a mano). Check/tachado, cantidad opcional y equivalencias (ej. 3 dientes = 1 cabeza de ajo).

3. Tareas domésticas (nueva zona)

  • Reparto automático del fin de semana (sábado + domingo) entre las 3 personas del hogar.
  • Catálogo inicial de 15 tareas con peso de esfuerzo (1-3): pasar la aspiradora, limpiar el baño, sacar la basura, cocinar el fin de semana, etc.
  • Algoritmo: greedy equilibrado por peso con rotación semanal; cada persona reparte sus tareas entre sábado/domingo balanceando esfuerzo. Reemplaza solo asignaciones generadas previas; las manuales (generado=false) se respetan.
  • Cualquier usuario autenticado puede generar el reparto y añadir tareas al catálogo; el admin Fiti gestiona usuarios.
  • Config tareas_personas (ids de Fiti,Mar,Jose) en la tabla Configuracion; las personas se calculan por prefijo de nombre para el reparto (los posibles prefijos quedan en la config por si cambian los nombres).

3.1. Notificaciones

  • Al generar el reparto o asignar una tarea a mano, cada persona con tareas pendientes recibe una notificación en la app con el detalle («Fiti te ha asignado N tareas...» / «Mar te ha asignado la tarea...»).
  • Al marcar como finalizada una tarea, se notifica a quien la asignó («Jose ha finalizado la tarea «Limpiar el baño»»).
  • Modelo Notificacion (titulo/mensaje/tipo/leida) + campo asignadaPorId en AsignacionTarea. Rutas: GET /api/notificaciones, GET /no-leidas, PATCH /:id, POST /leer-todas. En el web: campana con badge de no leídas (polling 30 s) y panel con historial.
  • Corrección: el generador ya no asigna una tarea a una persona que la tiene asignada a mano (fallo de constraint @@unique(usuarioId,tareaId,semana)).

4. Entorno y arquitectura

  • Windows (win32), PowerShell 5.1. Stack replicado de quiniela_app_new / GM-PrintFlow: monorepo app/ con packages/api (Express + TypeScript + Prisma) y packages/web (Vite + React + TypeScript + Tailwind 4).
  • Base de datos: PostgreSQL 15 en contenedor Docker, puerto 5435 (user/db/pass = cookplan). Contenedor cookplan-db.
  • Puertos locales: API 3004, dev server web 5176 (con proxy /api y /uploads → 3004).
  • Tema: dark por defecto con modo claro; clases utilidades card, btn, input, badge; acento naranja (--color-accent-500:#f97316).

5. Base de datos (Prisma)

  • Migraciones aplicadas: 20260919091315_init, 20260919100000_tokens_usuario_unico (usuarioId único en TokenConfirmacion/TokenRecuperacion) y 20260919110000_tareas_domesticas (enum DiaSemanaTarea, modelos TareaDomestica y AsignacionTarea con @@unique([usuarioId,tareaId,semana])).
  • ⚠ prisma migrate dev es interactivo y falla en consola no interactiva → las migraciones se escriben a mano en prisma/migrations/<epoch>_nombre/migration.sql y se aplican con npx prisma migrate deploy + prisma generate.

6. API REST (packages/api)

/api/health · /api/auth (login/registro/confirmar/recuperar/reset/perfil+logo)
/api/recetas  CRUD + foto · /api/plan (get/guardar/generar/sugerencias)
/api/lista-compra (get/crear/patchear/borrar/generar desde menú)
/api/tareas  reparto + catálogo + asignaciones · /api/usuarios (admin)
  • JWT Bearer; middleware de auth con req.usuario; subida de fotos con multer 2.x + sharp (WebP).
  • Email: si existe SMTP_HOST envía correos reales; si no, el enlace se muestra por consola (estilo quiniela).

7. Frontend web (packages/web)

  • Páginas: Login, Register, Confirmar, Recuperar, Reset, NotFound, Recetas (grid + CRUD + ver), Plan (tabla semanal + picker con sugerencias), Lista, Tareas domésticas, Perfil, Usuarios (admin).
  • Contextos: Auth (cp_token/cp_usuario, guardas Privado/Admin) y Tema (cp-theme). Axios centralizado con interceptor de token y manejo 401.
  • Build de producción en verde (tsc && vite build); proxy del dev server probado de extremo a extremo (login a través de 5176).
  • Capacitor 8: plataforma Android añadida (appId com.cookplan.app, webDir dist). Para la app real hay que compilar con VITE_API_URL apuntando a la API desplegada.
